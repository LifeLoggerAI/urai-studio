## Limitations and blocking gates
1. **Time-of-check/time-of-use:** The route recheck occurs before an independently awaited Firestore Admin transaction; it is not an authorization check inside that transaction. If membership or deletion state changes between preflight and commit, a stale write may still occur. A true race-proof owner admission requires transaction-bound current authority or an enforceable server-side generation/fence, plus concurrent revoke tests. Do not label R865 revocation-race safe.
2. **Authority truth:** `memberships` documents are denied to clients in Firestore Rules, but audit trusted provisioning and actual deployed Rules/IAM before granting protected media access. Ordinary membership does **not** issue Privacy C6 positive private Life Movie consent.
3. **Owner read timing:** GET authorization occurs before the Firestore query, not atomically at query execution. Require native concurrent revoke/query tests and per-object authorization for private data.
4. **Role migration:** Global `studioUsers` and tenant `memberships` role semantics can differ; owners/editors must be migrated intentionally, with denied visitor/viewer write cases verified. A token lacking signed tenant stays rejected.
5. **Retry idempotency remains open:** Lost HTTP response after committed draft/brief/project transaction may create duplicate IDs. Actor+tenant+canonical-request digest must be bound atomically and tested with same-key retries and conflicting input.
6. **Broader HOLD:** R858/R859 server-owned job audit security drafts unmerged; historical `uid`-only Studio project schema unconverted; Jobs #252 privileged Storage post-revocation future-write fence and trusted signed Privacy C6 remain hard-off; real source-to-protected MP4/SRT→owner-only Spatial Replay→derivative deletion and device acceptance not certified.
